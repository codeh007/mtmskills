# 诊断第三方模型中转

先区分运行本技能的诊断环境和实际发生问题的客户端，再用已有入口收集证据。目标是区分客户端、本地网络、中转和上游问题，并生成可复核的报告。

默认执行只读、低频检查。只使用当前环境已有的客户端、命令、日志和网络工具；缺失能力写入报告。修改配置、切换网络、重启客户端、安装工具或持续测试前，先取得明确授权。

请求用户提供材料时，只收集故障前后最小时间窗且已脱敏的片段；完整日志、配置文件和环境变量留在用户本地。

## 1. 识别当前环境

诊断环境和故障客户端可能相同，也可能不同。先确认诊断环境能提供哪些信息：

- **ChatGPT App**：检查应用是否显示版本、状态、反馈或诊断入口，以及是否支持导出日志
- **Codex 命令行、编辑器插件或远程客户端**：只从正在使用的客户端确认可用的状态、配置和日志入口，再使用这些入口
- **其他客户端**：记录界面错误、版本和时间；按现有权限使用浏览器、操作系统或服务方提供的诊断信息

再记录故障客户端、操作系统、模型、中转主机名和代理或虚拟专用网络（VPN）状态。只记录当前环境或用户能确认的事实，其余项目标为“未知”。

完成：已列出诊断环境、故障客户端、版本、可用诊断入口和缺失能力。

## 2. 复现并分类问题

记录准确症状、错误文本、发生频率、首次与最近一次时间、触发操作、上次正常时间和近期变化。没有明确症状时，先将其标为“未知”，再从描述或现有日志中取得一个可观察失败。

使用合成的无敏感输入创建最小探针。让探针经过实际请求路径，但不携带项目内容或触发工具调用。为重复检查设置次数或时限上界。

若诊断环境不能直接操作故障客户端，给用户一项明确的探针操作，并请其返回时间、结果分类、耗时、可见错误或截图，以及能看到的请求标识。

将每次结果分类为：正常、异常缓慢、重连后成功、服务返回错误、连接失败、流中断或超时。按正常记录或明确阈值判断“异常缓慢”。

完成：同一探针可以重复执行并记录每次结果、时间和分类；若当前环境无法发起或观察探针，已写明缺少的能力和最小下一步。

## 3. 收集并比较证据

按请求经过的环节记录最少必要信息：

| 环节 | 记录内容 |
| --- | --- |
| 故障客户端 | 可见错误、重试或重连、操作与发生时间 |
| 本地连接 | 当前环境可见的域名解析、建立连接、加密连接握手、代理或 VPN 路径 |
| 请求与流式响应 | 服务状态码、首个响应与总耗时、流是否完整结束、请求标识 |
| 中转与上游 | 服务方提供的入口接收情况、排队或限流、上游状态、重试、超时和各段请求标识的对应关系 |
| 本机资源 | 仅在本地工具也变慢时记录处理器、内存、磁盘或进程阻塞 |

把所有记录统一到本地时间和协调世界时（UTC），记录样本数并优先列出原始值或范围；样本较多且条件可比时，可补充中位数等汇总值。单独的连通性或路由检查不能证明应用请求故障。

若缓慢发生在本地工具阶段，在正常工作中另行记录各阶段耗时，不把工具调用加入中转探针。

列出所有仍与证据相容的假设并排序。每个假设都写明预期现象和反证。每次只改变一个变量，并复跑相同探针；切换网络、代理、VPN、客户端或直连上游前先取得授权。

完成：每个失败已定位到最窄的已知边界，或明确写出缺少哪一侧的日志、时间或请求标识。

## 4. 编写诊断报告

使用以下结论等级：

- **已确认**：故障可重复复现，多轮“原设置、改变一个变量、恢复原设置”对照都稳定翻转结果，或两侧证据直接显示同一请求在哪个边界因何失败
- **较可能**：至少两项独立证据一致，但缺少决定性的对照或服务端证据
- **证据不足**：无法复现、样本不足、关键边界不可见或证据冲突

报告包含：

1. 摘要、用户影响和结论等级
2. 客户端、环境、时间窗、约束和脱敏说明
3. 症状、复现方法、样本结果和各阶段耗时
4. 原始观测、解释、反证和仍可能的原因
5. 按客户端、网络、中转和上游划分的下一步
6. 可取得的脱敏证据，例如操作步骤、界面错误或截图、命令、日志片段和请求标识

向服务方请求协查时，提供本地与 UTC 时间窗、中转主机名、模型、样本数、状态码、阶段耗时、请求标识对应关系和最小复现步骤。请对方核查入口、鉴权、限流、队列、上游、重试、超时和流式断开位置。

将访问令牌、API 密钥、登录 Cookie、授权头、URL 密钥、请求正文、提示词、模型回复、工具输出和个人路径替换为 `[已脱敏]`。发布报告前再次检查。

完成：每个判断都能追溯到证据。只有“已确认”可以写成根因；其他等级必须给出取得决定性证据的最小下一步。
