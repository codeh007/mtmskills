# 第三方模型中转诊断

把一次诊断做成可复跑的差分实验。默认只执行只读、低频探测；修改配置、切换 VPN、代理或网络、重启客户端、安装工具和持续压测都需要用户明确授权。

本技能只处理 provider 已能加载且请求至少偶发成功后的运行时连接与性能问题。安装、登录、provider 配置、凭据维护或模型切换使用 `gomtm-codex-dev`；诊断结束后需要修复配置时也交给该技能。

## 证据边界

- 只记录完成归因所需的配置键名、非敏感值、布尔状态、主机名和脱敏日志。将 token、API key、cookie、`Authorization`、URL 查询密钥、完整请求正文、提示词及个人路径替换为 `<redacted>`。
- 在本机读取配置、环境变量和日志时直接筛选所需字段，不输出完整的 `auth.json`、`.env`、`config.toml` 或日志文件。报告发布前再做一次秘密与隐私检查。
- 把“当前请求成功”“服务方称运行正常”和“VPN 已关闭”作为待核验线索。一次成功样本不能证明持续流稳定，也不能排除间歇性故障。
- 将原始观测与解释分栏记录。每个结论都保留时间戳、采集方式、样本量和反证。

## 1. 冻结症状与判据

先记录：

- 客户端形态与版本、操作系统、模型、provider 和中转主机名。
- 用户看到的准确症状、错误摘要、发生频率、首次与最近一次时间，同时记录本地时区和 UTC。
- 能触发问题的操作、正常基线、最近配置或网络变化，以及问题只影响模型响应还是也影响本地工具阶段。

用户没有提供具体症状时，把“频繁自动重连且任务体感缓慢”标为待确认症状；先从现有日志或一次低成本复现中确认，不直接据此归因。

定义一个走真实客户端路径的最小探针，明确每次运行的成功条件、失败条件和计时点。间歇性问题使用有次数或时限上界的重复采样，不进行负载测试。

**完成条件：** 已有一个可复跑探针，能够把每次尝试判为成功、连接失败、流中断或超时；若无法构造探针，已列出缺少的日志、访问权或复现条件。

## 2. 还原有效请求路径

按当前客户端版本和 `codex --help` 识别可用诊断入口。Codex 配置层级与 provider 字段以[官方 Advanced Configuration](https://learn.chatgpt.com/docs/config-file/config-advanced)为准，不从旧命令或单个配置文件推断有效配置。

只读确认：

- 实际 Codex home、参与合并的配置层、活动 provider、模型、base URL 主机名和 wire API。
- 凭据来源的类型与变量名，不读取或回显凭据值。
- 客户端进程实际继承的 HTTP(S)/ALL/NO proxy 状态、VPN 状态、DNS 解析器、地址族和出口路径。
- 症状时间窗内的客户端 retry、backoff、reconnect、HTTP 状态、流结束事件、请求 ID 和错误链。

**完成条件：** 能描述 `客户端 -> 本机代理或 VPN -> 中转入口 -> 上游` 的实际或待证请求路径，并为每一段标明证据来源；无法确认的段明确标为未知。

## 3. 建立可证伪假设

根据症状和路径列出 3 至 5 个排序假设。每个假设都写成：

> 如果 `<原因>` 成立，那么 `<单变量变化或边界观测>` 应出现 `<可观察结果>`；若未出现，则降低该假设的排序。

至少覆盖仍与证据相容的客户端、DNS/网络、代理或 VPN、中转入口和上游分支。为每个假设选择能区分它与相邻假设的最小探针，优先比较同一低成本请求，保持模型、输入和时间窗一致。

**完成条件：** 每个假设都有预测、探针和反证条件，不存在只凭直觉或服务方口头状态成立的假设。

## 4. 分层测量并对时

改变一个变量后立即复跑第 1 步探针。切换网络、VPN、代理、地址族、客户端或直连上游只在用户授权且具备相应凭据时执行；不可执行的比较保留为证据缺口。

| 层级 | 最少记录的观测 |
| --- | --- |
| 客户端 | 阶段、重试与 backoff、重连次数、错误链、流是否正常结束、请求 ID |
| DNS | 解析器、A/AAAA/CNAME 结果、解析耗时、失败或结果漂移 |
| TCP/TLS | 目标地址、连接耗时、TLS 握手、SNI/证书异常、IPv4/IPv6 差异 |
| HTTP/流 | 状态码、首包或首 token、总时长、最长流间隔、完整结束事件、响应请求 ID |
| 中转/上游 | 入口是否收到请求、排队时间、限流、上游状态、重试、超时或断流位置 |
| 本机资源 | 仅在体感慢可能来自本地工具时记录 CPU、内存、磁盘或进程阻塞 |

短请求成功只能证明当次基本连通。自动重连问题需要覆盖真实持续流；ICMP 丢包或 traceroute 单独不作为应用故障归因。将客户端日志、探针和服务端记录统一到同一时区，并优先通过请求 ID 对齐。

报告每组样本的 `n`、成功率、错误分类和各阶段耗时。样本足够时给出 p50/p95；样本较少时保留原始值或范围，避免伪精度。

**完成条件：** 每个已观察失败都能定位到最窄的已证实边界，或明确指出缺少哪一侧的时间、请求 ID 或日志；所有执行过的探针都有命令或操作、时间、退出状态和脱敏结果。

## 5. 归因与交付

统一使用以下结论等级：

- `confirmed`：复现成立，单变量差分能翻转结果，或客户端与服务端有同一请求的直接关联证据。
- `probable`：至少两项独立证据一致，但缺少决定性的差分或服务端关联。
- `inconclusive`：样本不足、无法复现、关键边界不可见或证据互相冲突。

始终交付 Markdown 报告。工作区已有报告路径约定时遵循该约定；否则在最终回复中提供报告。报告包含：

1. 摘要、结论等级和用户影响。
2. 范围、时间窗、时区、约束与脱敏规则。
3. 脱敏后的环境和有效请求路径。
4. 复现判据、样本矩阵、阶段耗时与错误分布。
5. 原始观测、解释、反证及已排除或仍可能的假设。
6. 按本地、网络、中转和上游 owner 划分的下一步与复验方法。
7. 完整但脱敏的命令、退出状态、关键日志和请求 ID 附录。

需要中转运维配合时，另给一段可直接转发的核查请求，包含本地与 UTC 时间窗、中转主机名、模型、wire API、样本量、状态码、阶段耗时、请求 ID 和最小复现步骤；明确请求对方核查入口日志、鉴权或限流、队列、路由、上游状态、重试/超时和流式缓冲或断开位置。

**完成条件：** 报告中的每个判断都可追溯到证据；只有 `confirmed` 才表述为根因。其余情况明确写为 `probable` 或 `inconclusive`，并给出获得决定性证据所需的最小下一步。修复获授权并完成后，用同一探针补充前后对比。
