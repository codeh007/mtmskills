# GOMTM Listview Design

## Overview

列表视图首先是“进入下一步操作的摘要入口”，不是把一条记录的全部字段铺满屏幕。

当一个页面的核心任务是扫描项目、识别状态、执行常用动作、进入详情，那么它更像 `Item/Card` 组合的列表，而不是数据表。

## Core Rule

先判断用户在这个页面上的主要任务：

1. 如果主要任务是“扫描对象、看摘要、做常用动作、进入详情”，优先做列表项视图。
2. 如果主要任务是“逐列比较大量同构字段、排序、批量筛选、复制表格数据”，才优先考虑 table。

设备、任务、配置、联系人、账号、浏览器 profile 这类“运营对象列表”，默认更接近列表项视图，而不是 spreadsheet。

## Listview Principles

### 1. Summary First

列表项只显示摘要信息：

1. 主身份信息
2. 1 到 3 个最重要的状态/分类标签
3. 1 到 3 组辅助摘要
4. 1 到 2 个高频动作
5. 清晰的详情入口

如果一个列表项需要完整展示所有字段，说明它不再是列表，而是在错误地承担详情页职责。

### 2. Mobile First

先按移动端设计，再向宽屏扩展。

移动端下：

1. 信息应纵向堆叠
2. 标题和状态必须先出现
3. 动作区应在底部或右侧清晰聚合
4. 不能依赖横向滚动才能读懂一项

桌面端只是在此基础上增加更舒展的分栏，而不是回退成宽表格。

### 3. One Clear Primary Action

每个列表项至少应有一个清晰的主入口：

1. 查看详情
2. 编辑
3. 打开
4. 继续处理

常用动作可以并列，但不应淹没主入口。

### 4. Detail Has A Home

列表视图通常伴随详情入口。

详情承接方式优先级：

1. 独立详情页：适合设备、任务、配置等信息较多、动作较多的对象
2. 对话框：适合轻量预览或少量补充信息
3. 行内展开：只适合极少量附加信息，不适合完整详情

如果详情内容包含完整命令、错误全文、长文本、多个次级动作，优先独立详情页。

对 gomtmui 中的设备类列表，默认规则更硬一些：

1. 设备详情默认优先独立详情页
2. 不要先做弹窗，除非明确只需要轻量预览
3. 命令参考、错误详情、诊断入口这类内容都应推动你选择详情页

## Item Anatomy

一个健康的列表项通常分成 4 层：

1. Header
2. Summary facts
3. Optional warning/error block
4. Footer actions

### Header

Header 负责回答“这是什么”：

1. 标题：例如设备名、任务名、配置名
2. 次标识：例如 ID、slug、provider 内标识
3. 紧邻状态 badge：例如在线/离线、已纳管/失败

### Summary Facts

Summary facts 负责回答“现在需要知道什么”：

1. 最近事件
2. 最近心跳
3. 接入摘要
4. 平台 / provider
5. 关键 owner / category / group

一次最多展示少量关键摘要。其余内容进入详情。

当空间紧张时，推荐保留优先级：

1. 标题
2. 状态 badge
3. 一个最关键的分类 badge（平台或 provider）
4. 最近事件
5. 最近心跳

优先降级或移除：

1. 次要分类标签
2. 长接入摘要
3. 错误全文
4. 命令参考

### Optional Warning Block

错误或异常可以展示，但必须有边界：

1. 默认只显示短摘要或 1 到 2 行
2. 不在列表里完整铺开长错误全文
3. 错误视觉上应独立成块，而不是和普通摘要混在一起

### Footer Actions

底部动作区应聚焦常用操作：

1. 主动作一个最突出
2. 次动作 1 到 2 个即可
3. 低频或长文本信息不要伪装成动作堆在这里

## Device List Guidance

设备类列表项推荐信息层级：

1. 主标题：设备名
2. 次信息：设备 ID
3. 分类 badge：平台、provider
4. 状态 badge：在线/离线、业务状态
5. 摘要信息：
   - 接入摘要
   - 最近事件
   - 最近心跳
6. 条件性错误摘要：仅在存在错误时显示
7. 动作：
   - 查看详情
   - 归档设备 / 常用动作

不推荐在设备列表项中直接展示：

1. 全量命令列表
2. 错误全文
3. 所有 metadata 字段
4. 多段说明文案
5. 大量同级按钮

这些应该进入设备详情页。

设备列表项的推荐布局蓝图：

1. 第一行：标题在左，状态 badge 在右
2. 第二行：ID 与分类 badge
3. 第三到四行：2 到 3 个摘要事实块
4. 条件出现：短错误块
5. 最后一行：`查看详情` 主动作 + 1 个次动作

## Table Anti-Patterns

以下情况通常是在滥用 table：

1. 页面本质是对象列表，却为了“字段整齐”硬做成多列表格
2. 用户需要横向滚动才能看懂一个列表项
3. 每行同时展示完整详情、完整错误、完整动作清单
4. 所有列都同等强调，没有主次
5. 列表项没有明显详情入口
6. 操作列堆满命令文本、链接和按钮

一旦出现这些迹象，优先把页面改回列表项组合。

## Shadcn Composition

优先使用组合，而不是把 `Table` 当默认答案。

常用组合：

1. `Card` / `CardHeader` / `CardContent`
2. `Badge` 展示状态、分类
3. `Button` 展示高频动作
4. `Separator` 隔开错误区、动作区
5. 需要空态时用已有空态样式或 `Empty`

在 gomtmui 里，如果一项内容更像“可进入详情的运营对象卡片”，优先：

1. `Card` 作为 item container
2. `flex flex-col gap-*` 组织垂直信息层级
3. `md:grid` 或 `md:flex-row` 只用于桌面扩展摘要布局

不要为了视觉对齐回退到 `Table`。

## Decision Rules

做列表视图前，先回答：

1. 这一项的“标题”是什么？
2. 用户在 2 秒内最想知道的 3 件事是什么？
3. 用户在列表页最常做的 1 到 2 个动作是什么？
4. 哪些信息应该被推迟到详情页？
5. 移动端是否能在不横向滚动的前提下读懂一项？

如果回答不出来，先不要写 JSX。

## Example

设备列表从宽表格重构为摘要卡片时：

错误做法：

1. 一行里平铺名称、provider、接入摘要、状态、最近事件、最近心跳、错误、5 条命令
2. 用户必须左右滚动
3. 每条设备像一张压缩后的详情页

正确做法：

1. 顶部只突出设备名、ID、状态、平台/provider
2. 中部只保留接入摘要、最近事件、最近心跳
3. 错误存在时单独显示短摘要
4. 底部只保留“查看详情”和“归档设备”
5. 完整命令移到 `/dash/devices/[deviceId]`

## Review Checklist

在声称列表视图设计完成前，逐项检查：

1. 这是不是列表项，而不是伪装成列表的详情页？
2. 移动端是否不依赖横向滚动？
3. 标题、状态、主动作是否足够突出？
4. 是否只展示摘要，而不是展示全部字段？
5. 是否有清晰详情入口？
6. 是否避免了把命令、长文本、低频信息塞进列表？
7. 是否优先使用了 shadcn 组合而不是 table？

## Common Mistakes

### Mistake: “字段很多，所以用 table 最稳”

现实：字段多不等于应该全部出现在列表页。先删减到摘要层。

### Mistake: “错误信息很重要，所以直接全展示”

现实：重要不等于要在列表里完整展开。摘要 + 详情才是更稳的阅读路径。

### Mistake: “桌面端够宽，所以可以做成大表格”

现实：这会直接破坏移动端，也会削弱列表的主次结构。

### Mistake: “命令文本也是常用操作，所以放列表里” 

现实：命令参考通常属于详情内容，不属于列表项摘要。

## Red Flags

出现以下念头时，应立即停下来复查：

1. “这页看起来信息不全，所以把更多字段塞进去”
2. “为了整齐，把它改成 table”
3. “既然有空间，把完整错误和命令都放列表里”
4. “详情页还没做，先把详情塞回列表项”

这些通常意味着页面正在从“列表”滑回“混乱详情页”。
